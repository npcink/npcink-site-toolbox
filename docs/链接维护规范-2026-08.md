# 链接维护规范

> 日期：2026-08-07
>
> 适用范围：插件运行界面、README、WordPress.org `readme.txt`、插件内置帮助页和 VitePress 文档。

## 链接分类

### 项目自有链接

包括 GitHub 仓库、作者站点、在线文档和插件内置帮助页。这类链接必须在公开前完成 DNS、TLS 证书、部署和真实访问验证。未就绪的地址只能显示为“建设中”文本，不得生成可点击链接。

插件内功能的基础使用教程优先放在插件内置帮助页，确保外部文档站不可用时仍可查看。在线文档只作为扩展内容，不应是基础操作的唯一入口。

### 第三方链接

包括云厂商、分析平台、法律条款和 WordPress/GitHub 文档。应优先使用官方 HTTPS 地址，并允许对需登录、区域限制或反爬的目标建立明确白名单。白名单只表示不在 CI 中强制联网验证，不表示永久免于复查。

### 站点内部链接

后台页面使用 `admin_url()`、`rest_url()` 或现有语义导航工具生成，不得假设 WordPress 安装在域名根目录。Markdown 相对链接的目标文件必须存在。

### 占位和示例

`example.com`、`github.com/owner/repository`、`your-login-name` 等只能用于代码块、输入占位或测试数据。“待完善”、`TODO`、空字符串和示例 URL 不得被渲染为可点击链接。

## 修改与同步

修改公开 API 或用户功能时，必须同时检查：

1. 实现合同或开发说明；
2. 插件内置帮助页；
3. VitePress 用户教程；
4. README 和 WordPress.org `readme.txt` 中的公开入口；
5. 相关合同测试和示例响应。

历史文档中的旧地址如果是理解历史所必需，应明确标注为“历史仓库”或“历史链接”，同时给出当前维护入口。

## 验证门槛

日常修改至少执行：

```bash
composer links:check
git diff --check
```

`composer links:check` 负责可重现的离线合同：

- 公开页面不再使用旧 GitHub 仓库身份；
- 未就绪的文档域名不对外宣传；
- 静态用户链接不使用明文 HTTP；
- README 和 VitePress 的内部 Markdown 目标存在。

联网死链检查不放入每次 CI，避免第三方反爬、登录和区域网络导致随机失败。发布前应对项目自有域名和后台可点击链接做一次真实 HTTP/TLS 检查，定期审计第三方链接的重定向和最终落点。
