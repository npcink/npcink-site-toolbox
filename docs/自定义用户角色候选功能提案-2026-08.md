# 自定义用户角色候选功能提案

> 日期：2026-08-06
>
> 状态：候选想法，暂缓实现
>
> 范围：Npcink Site Toolbox 本地 WordPress 用户角色管理

## 一、问题与定位

站点所有者可能需要创建区别于 WordPress 内置订阅者、作者、编辑和管理员的用户角色，并通过可理解的界面选择角色权限。该能力属于本站本地用户管理工具，符合 Npcink Site Toolbox 的产品边界。

面向用户的功能名称应使用“自定义用户角色”，避免使用含义不够明确的“自定义身份”。现有“内容与页面 → 权限”管理的是未登录访问限制；若将来实现，应将其改名为“访问限制”，并为“用户角色”提供独立的二级标签，避免混淆两种权限模型。

本提案只记录方向，不代表版本承诺、开发排期或已接受的架构决策。

## 二、候选 MVP

- 创建角色：填写显示名称和不可变的唯一标识；
- 复制角色：以 WordPress 现有角色为权限模板；
- 权限选择：按内容、媒体、页面、评论、用户和站点管理分组展示 capability；
- 编辑角色：第一版只管理由本插件创建的角色；
- 删除角色：删除前必须处理仍使用该角色的用户；
- 使用情况：显示各角色关联的用户数量；
- 风险提示：为敏感 capability 提供中文说明、风险等级和二次确认。

## 三、安全与数据边界

- 第一版不得修改或删除 WordPress 内置角色，尤其是 `administrator`；
- 不得让站点失去最后一个具备有效管理权限的管理员；
- `manage_options`、`edit_users`、`promote_users`、`delete_users`、`unfiltered_html`、`install_plugins` 和 `update_plugins` 等能力应视为高风险；
- 所有角色写操作必须同时进行 `manage_options` 权限检查、REST nonce 校验、输入净化和服务端 capability 白名单校验；
- 角色唯一标识创建后不得修改，避免已有用户关联失效；
- 非空角色不得直接删除，必须先迁移用户或取消操作；
- 第一版只考虑当前站点，不承诺 WordPress 多站点网络级同步；
- 不建立平行权限系统，角色与 capability 继续以 WordPress 原生数据为事实源。

插件如需识别自身创建的角色，只保存最小的角色标识清单；不得把完整角色权限复制进普通设置 Schema，也不得默认接管其他插件创建的角色。

## 四、候选实现方向

后端优先复用 WordPress 原生角色 API：

- `add_role()`；
- `get_role()`；
- `WP_Role::add_cap()`；
- `WP_Role::remove_cap()`；
- `remove_role()`。

后台可通过受保护的 REST 接口读取角色、权限目录和用户数量，并执行创建、更新、迁移后删除等操作。接口设计必须先明确幂等性、错误响应、内置角色保护、当前管理员保护和多站点行为，再进入实现。

## 五、明确非目标

第一版不考虑以下能力：

- 按单个用户直接附加 capability；
- 按分类、文章或其他条件动态授权；
- 角色导入、导出或跨站点同步；
- 修改 WordPress 内置管理员角色；
- 自定义数据库权限模型；
- Cloud、队列、计费、审批或跨仓库角色真相。

## 六、进入开发前的准入条件

只有在真实站点出现明确使用场景，并能回答以下问题后，才考虑进入排期：

1. 目标用户为什么不能直接使用 WordPress 内置角色？
2. 高频需要创建的是哪类角色，最小权限模板是什么？
3. 是否需要管理其他插件创建的角色，若需要，所有权和回滚边界是什么？
4. 删除角色时采用强制迁移还是仅允许删除空角色？
5. 多站点明确支持、明确不支持，还是只读提示？
6. 是否能通过聚焦 PHPUnit、REST 安全测试、后台 Vitest、`composer test` 和 `composer phpstan` 证明安全合同？

## 七、回滚原则

未来若实现，应保证停用或移除该管理功能不会自动删除角色、撤销用户权限或迁移用户。任何角色删除和用户迁移都必须是管理员显式发起、可预览并确认的操作。
