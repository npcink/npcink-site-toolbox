## 一、问题治理原则

1. **先建立边界，再修代码。** 每个工作包开始前写出变更信封：目标仓库、聚焦模块、预期改动、明确非目标、公共契约、预期文件、禁止变更区域、必跑门禁、跨仓库影响和回滚方案；一次只处理一个模块或紧密相关工作包。
2. **只修可复现且影响行为的问题。** 样式偏好、工具误报、无消费者旧表面和外部服务不可验证项要与真实 Bug 分开记录。真实 Bug 先补一条“旧实现必失败”的回归，再做最小修复。
3. **单一事实源优先。** Registry、配置 Schema、版本号、发布 slug、REST namespace、内置帮助、README、WordPress.org 文档和 docs-site 教程不能靠记忆同步；公共契约变化必须有契约测试。
4. **安全边界必须可证明。** 凭据只显示状态；REST 分别验证匿名、低权限、管理员、畸形输入和泄漏；清理、媒体删除和卸载在隔离环境验证；外部 API 设置超时、响应上限、缓存和失败降级。

## 二、推荐分阶段工作流

### 阶段 A：基线与分类

运行 `git status --short --branch`，阅读 README 和最近台账；建立问题矩阵，按 P0/P1/P2 区分用户影响、数据风险和发布风险。

### 阶段 B：契约先行

为激活路径、REST 权限、数据清理、Cron 生命周期、版本一致性、平台兼容和卸载行为增加 PHPUnit/静态契约，契约名称描述业务不变量而不是实现细节。

### 阶段 C：最小实现与局部验证

先运行聚焦测试使旧实现失败，再修改最小范围代码；随后运行对应 PHP、TypeScript、编辑器和构建测试，避免把重构和行为修复混在一起。

### 阶段 D：真实 WordPress 验证

使用真实 `serialize_block()` + `do_blocks()`、真实 REST 请求和真实后台页面验证，不能只直接调用渲染回调。最低边界覆盖 WordPress 6.3/PHP 7.4，当前版本覆盖 WordPress 7.x/PHP 8.x；主题兼容至少包含一个核心区块主题和当前项目主题。

### 阶段 E：发布候选与清理

构建唯一候选 ZIP，记录版本、条目数、大小和 SHA-256。用该精确 ZIP 在干净 WordPress 环境安装、激活、访问后台/REST/区块，再运行官方 Plugin Check。测试容器、卷、网络、用户、应用密码、Transient、Cron 和测试内容逐项清理并复核无残留。

### 阶段 F：收尾与交付

```bash
composer test
composer phpstan
pnpm --dir vite build
composer release:build
composer release:verify -- npcink-site-toolbox.zip
git diff --check
```

暂存前检查 `git status --short --branch` 和 `git diff --stat`；只暂存本轮文件。提交前检查 `git diff --cached --stat` 与 `git diff --cached --name-only`，提交后检查 `git show --name-status --stat HEAD`。获得明确授权后再 push。

## 四、已知边界与后续触发条件

- 搜索健康模块关闭时相关路由返回 404，这是 opt-in 设计；若 UI 改为默认请求，必须同步改变路由契约或前端门控。
- OSS 真实云端上传仍需目标站点使用可撤回测试 Bucket 验证；本地签名和失败回退测试不能替代供应商端到端证明。
- 当前主题与核心区块主题通过，不代表所有第三方主题；修改前台渲染、评论过滤或 CSS 时应补窄测试。
- 搜索健康的严格并发限流只约束统计写入，不阻断用户搜索；锁竞争或锁存储异常时保守跳过本次统计。其他 Transient 计数器仍不能自动继承该强一致承诺。
