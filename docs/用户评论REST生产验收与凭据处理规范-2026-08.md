# 用户评论 REST 生产验收与凭据处理规范

> 日期：2026-08-07
>
> 状态：已采用
>
> 适用范围：用户评论 REST 的 Local 联调、预发布验收、生产站点冒烟和 AI 评论助手接入

## 一、目标与边界

生产验收的目标是证明最终站点上的真实链路可用，而不是再次扩大功能范围。验收只操作专门创建的临时评论，不读取、修改或删除其他用户和既有业务评论。

应用程序密码只负责认证请求身份；服务端的资源所有权检查仍以当前认证用户 ID 为准。验收不能使用管理员 Cookie、客户端传入的用户 ID、评论邮箱或昵称代替真实 Basic Auth。

## 二、开始前检查

1. 确认站点使用有效 HTTPS，最终 URL 没有降级到 HTTP；
2. 确认 `/wp-json/` 可访问且包含 `npcink-site-toolbox/v1` 命名空间；
3. 未认证访问 `/me/comments` 应返回 `401`；
4. 确认评论 REST 总开关已开启；
5. 准备一个专门用于客户端接入的 WordPress 用户；
6. 为每个客户端单独创建应用程序密码，并记录对应登录用户名；
7. 选择一篇已发布且允许评论的测试文章；
8. 约定唯一测试标记，例如 `NPCINK-REST-TEST-日期-随机值`。

不要通过公开作者 slug 推断登录用户名。WordPress 登录名、公开 slug、昵称和邮箱可能完全不同，应用程序密码必须与创建它的真实登录名配对。

## 三、凭据处理规范

- 不把应用程序密码写进仓库、Markdown、截图、日志、命令历史或自动化配置；
- 交互测试应通过隐藏输入、密钥管理器或 CI Secret 注入；
- 输出只记录 HTTP 状态、错误码、测试评论 ID 和处理结果，不回显 `Authorization` 请求头；
- 不把生产密码复制到 Local、Playground 或共享测试环境；
- 密码一旦出现在聊天、工单、截图或其他非保密渠道，验收完成后立即撤销并重新生成；
- AI 评论助手应使用独立密码，停用客户端时只撤销对应密码，不影响用户网页登录密码。

## 四、标准验收顺序

### 4.1 只读认证

使用登录用户名和应用程序密码读取一页自己的评论。期望 HTTP `200`，并确认响应不包含邮箱、IP 或应用程序密码。

认证失败时先检查用户名与密码是否属于同一账户，不要对公开用户 slug 批量猜测，也不要降低站点认证安全策略。

### 4.2 发布

向允许评论的文章发布带唯一测试标记的顶级评论。期望 HTTP `201`，保存返回的：

- 评论 ID；
- 当前状态；
- `expectedHash`。

初始状态可能是 `approved` 或 `pending`，取决于站点评论审核设置，客户端不能写死为必然通过。

### 4.3 修改

使用创建响应中的最新 `expectedHash` 修改测试评论。期望 HTTP `200`，确认正文已经更新，并保存新的哈希。

当前合同规定修改后进入 `pending`。如果返回 `409`，客户端应重新读取评论并让调用方确认，不得盲目覆盖。

### 4.4 单条删除与幂等性

删除测试评论，期望 HTTP `200` 和 `deleted`。随后读取 `status=trash`，确认该 ID 已进入回收站。

对相同 ID 再次删除，期望 HTTP `200` 和 `alreadyDeleted`。删除验收不应执行永久删除。

### 4.5 批量删除

重新创建两条带测试标记的评论，调用批量删除接口。期望：

- HTTP `200`；
- `summary.requested` 与提交数量一致；
- `summary.deleted` 等于成功处理数量；
- `summary.failed` 为 `0`；
- 每个 ID 都有独立结果。

批量操作是有界的部分成功语义，不应把它当成数据库事务。客户端必须逐项处理失败结果。

## 五、生产实测基线

2026-08-07 在真实 HTTPS 站点完成过一次完整验收，结果为：

- REST 索引和插件命名空间可访问；
- 未认证请求返回 `401`；
- 应用程序密码认证列表返回 `200`；
- 发布返回 `201`；
- 修改返回 `200`，内容更新且状态进入 `pending`；
- 单条删除返回 `deleted`；
- 回收站列表可确认测试评论；
- 重复删除返回 `alreadyDeleted`；
- 两条评论批量删除全部成功，失败数为 `0`。

该证据证明接口在真实 TLS、真实 WordPress 应用程序密码和真实评论数据流下可用。测试评论只进入回收站，没有永久删除。文档不保存生产用户名、密码、评论正文或具体评论 ID。

## 六、发布包与 Plugin Check 基线

同一开发节点使用仓库唯一发布入口生成 3.2.0 安装包：

```bash
pnpm --dir vite build
composer release:build
composer release:verify -- npcink-site-toolbox.zip
```

候选包基线：

- ZIP 根目录为 `npcink-site-toolbox/`；
- 228 个包内条目；
- 大小约 1.06 MB；
- 发布包结构、版本和 SHA-256 侧车校验通过；
- Plugin Check 2.0.0：初始候选为 `0` 个错误、`16` 个警告；2026-08-10 自动预审整改后的最终 ZIP 为 `0` 个错误、`2` 个警告；
- 本轮新增评论 REST 和帮助页没有引入新的 PCP 告警。

自动预审整改已将维护模板共享变量统一为 `npcink_site_toolbox_` 前缀。最终剩余 2 条警告来自对 WordPress 核心过滤器 `wp_generate_attachment_metadata`、`intermediate_image_sizes_advanced` 的调用被误判为自定义 Hook 未加前缀。它们应保留在发布验收记录中，不能简单用 `--ignore-warnings` 隐藏；若未来代码结构变化，应重新判断是否仍为误报。

PCP 必须检查最终 ZIP 解压内容，而不是直接扫描包含测试、文档、依赖和前端源码的开发仓库。

## 七、失败处理

| 现象 | 优先检查 | 禁止做法 |
| --- | --- | --- |
| REST 命名空间不存在 | 总开关、插件版本、路由注册 | 临时改核心路由绕过开关 |
| 未认证请求不是 `401` | CDN、缓存、安全插件、反向代理 | 先放宽认证规则 |
| 正确密码仍为 `401` | 登录用户名是否匹配、密码是否撤销 | 用公开 slug 持续猜测账户 |
| 发布失败 | 文章是否发布、评论是否开放、正文是否有效 | 改动既有业务评论验证 |
| 修改返回 `409` | 是否使用最新 `expectedHash` | 自动覆盖服务器新内容 |
| 删除返回 `409` | 是否已有有效回复 | 永久删除或直接改数据库 |
| 批量部分失败 | 逐项结果和所有权 | 重试整个批次并忽略已成功项 |

## 八、收尾清单

1. 确认所有测试评论都进入回收站；
2. 不永久删除测试记录，除非站点负责人另有数据保留要求；
3. 清理本地临时响应文件和终端中的敏感输出；
4. 撤销任何曾通过非保密渠道传递的应用程序密码；
5. 为正式 AI 评论助手重新创建独立密码；
6. 记录站点、日期、插件版本、HTTP 结果和失败原因，但不记录凭据；
7. 若代码或发布包发生变化，重新执行完整验收，不沿用旧 ZIP 的 PCP 结论。

## 九、维护门禁

评论 REST 或发布包边界变更后至少执行：

```bash
composer links:check
composer test
composer phpstan
pnpm --dir vite test:admin
pnpm --dir vite build
pnpm --dir docs-site build
composer release:build
composer release:verify -- npcink-site-toolbox.zip
git diff --check
```

正式发布前再对最终 ZIP 运行 Plugin Check，并按本规范完成一次真实 HTTPS 站点冒烟。
