# ADR-0005: 以精确发布包为 WordPress.org 验收对象

## 状态

已接受

## 日期

2026-08-17

## 背景

Npcink Site Toolbox 的首次 WordPress.org 审核先后暴露了资源加载、请求鉴权、链接、跨文件系统路径、公开源码、通用全局标识和远程内容规则问题。

这些问题分布在源码、构建产物、`readme.txt` 和最终 ZIP 四个表面。早期流程分别运行 PHPUnit、PHPStan、前端构建和 Plugin Check，但没有把它们绑定到同一个不可变发布包：

- 压缩文件的可读源码链接指向默认分支，而该分支落后于提交 ZIP；
- PCP 2.0.0 的零错误被误认为可以覆盖人工审核和未来规则；
- PCP 2.1.0 在同一发布周期新增 `OffloadedContent` 错误；
- 干净激活、WP_DEBUG、后台真实请求和 PCP 扫描依赖人工步骤；
- 已知 warning 与新增 warning 没有机器可判定的边界。

因此需要定义唯一发布事实源，并让源码、公开 tag、运行验证和扫描证据共同引用它。

## 决策

1. WordPress.org 发布验收对象是由仓库发布命令生成的精确 ZIP，而不是源码 checkout、dist 目录或事后重新构建的包。
2. 每次验收必须记录版本、commit/tag、ZIP SHA-256、WordPress/PHP/PCP 版本和完整 error/warning 数量。
3. `composer release:verify` 负责 ZIP 结构、版本、禁入路径、ASCII/大小写路径、源码 tag 和侧车哈希合同。
4. `composer release:wordpress-org-check` 在一次性 Docker 环境中安装同一 ZIP，开启 WP_DEBUG，执行真实前台和已登录后台 HTTP 冒烟，并安装官方最新版 Plugin Check。
5. PCP error 一律阻断。当前两条 WordPress Core hook warning 只通过文件、规则和 hook 名组成的窄允许项接受；其他 warning 阻断。
6. 扫描前后 ZIP SHA-256 必须一致；任何进入 ZIP 的文件变化都会使旧验收失效。
7. `readme.txt` 的可读源码和构建文件链接必须绑定目标版本 tag。tag 发布后必须匿名验证，且不得为了匹配新内容移动已公开 tag。
8. CI 强制执行上述门禁；人工仍负责阅读完整反馈、判断新规则、验证公开链接和上传同一制品。

## 理由

WordPress.org 审核面对的是上传的文件，而不是开发者本地意图。以精确 ZIP 为事实源，可以让以下问题进入同一证据链：

- 构建是否可重现；
- 压缩文件是否有对应可读源码；
- ZIP 路径是否可移植；
- 插件是否能在真实 WordPress 中激活和打开后台；
- WP_DEBUG 是否产生 notice、warning 或 fatal；
- 当前 PCP 是否存在错误或新增警告；
- 最终上传物是否与扫描对象完全一致。

窄允许 warning 而不是忽略全部 warning，使工具升级成为主动的变更检测器。新 PCP 规则导致 CI 失败是预期保护，不是流水线故障。

## 备选方案

### 只扫描开发仓库

拒绝。开发仓库包含测试、源码和依赖，缺少 `.distignore` 造成的真实发布边界，不能代表 WordPress.org 收到的文件。

### 在 ZIP 中包含全部前端源码

拒绝。可以满足可读性，但会扩大安装包、暴露开发依赖，并重复维护发布边界。精确公开 tag 加可复现命令能满足审核要求且保持安装包精简。

### 固定使用某一版 PCP

拒绝。固定版本有利于重现旧结果，却无法发现目录当前使用的新规则。发布门禁必须安装官方最新版，并记录实际版本。

### 只在发布者本地手工执行

拒绝。人工步骤容易漏跑、使用错误 ZIP 或忘记清理；CI 必须执行同一个仓库命令。本地运行仍保留，用于发布前复核和调试。

### 忽略全部 warnings

拒绝。warning 可能代表真实兼容、安全或目录问题。不得传入 `--ignore-warnings`；只允许经过人工判断且能用文件、规则和 API 精确描述的已知项。

### PCP 通过后重新打包或移动 tag

拒绝。重新打包会产生新的验收对象；移动公开 tag 会破坏源码可追溯性。需要修改时必须新建提交并重新走完整门禁。

## 影响

- CI 需要 Docker、数据库和外网下载官方 Plugin Check，发布任务耗时增加。
- PCP 或 WordPress 更新可能让以前通过的代码失败；维护者必须复核新结果，不能直接放宽规则。
- 每个 WordPress.org 版本需要预先确定 tag 名，并让 `readme.txt` 与版本保持一致。
- 发布证据可以被未来维护者和审核员通过 commit、tag 和哈希复查。
- `v3.3.1` 的运行包不包含此自动化脚本和内部文档；它们属于后续仓库治理提交，不改变已验证 ZIP。

## 回滚

不得回滚“精确 ZIP 是验收对象”这一原则。

如果 GitHub Actions、Docker Hub 或 WordPress.org 下载服务临时不可用，可以在本地运行同一命令并记录环境故障与完整证据，但不得跳过 WP_DEBUG、PCP、warning 复核或哈希一致性。恢复外部服务后，应补跑 CI；只有建立等价或更严格的替代门禁后，才能删除当前脚本。
