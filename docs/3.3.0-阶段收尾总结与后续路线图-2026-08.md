### 已关闭或不属于本仓库

- **Alt 自动写入**：不恢复。插件只报告问题，实际写入交给媒体库、内容人员或站点已有插件。
- **自定义用户角色**：保留候选提案；没有明确真实场景前不扩大权限和用户生命周期责任。
- **云端治理型 AI 写入**：Provider Runtime、提案批准、计费、队列和控制面属于其他仓库边界，不在本插件复制。

### 尚未完成但不阻塞 3.3.0 本地收口

- P1：使用真实凭据和可撤回 Bucket 完成对象存储供应商端到端验证；
- P2：依据真实用户环境选择第三方主题和页面构建器代表组合进行窄测；
- P2：积累至少 3 个可脱敏、可复验的 AI 诊断真实价值案例；
- P2：在明确账号、slug 和审核状态后执行 WordPress.org 正式提交或重新提交；
- P3：其他 locale、搜索体验、分类 SEO、传统 Widget 等候选增强。

这些事项未完成的共同原因不是代码门禁失败，而是仍需要外部凭据、代表环境、真实业务样本、账号授权或新的产品优先级。

## 三、实施阶段回顾

### 阶段 1：从用户视角建立问题清单

先走真实后台导航、设置、维护工具、空状态、错误状态和前台路径，再对照代码与测试。问题按以下口径分类：

- P0：会误导用户、破坏数据所有权或阻塞发布；
- P1：已有实现但缺真实外部验证；
- P2：需要代表样本才能证明价值或兼容性；
- P3：候选增强，不应挤占发布收口资源。

这一步的关键不是尽可能多地列问题，而是为每项写明用户影响、证据、非目标和完成标准。

### 阶段 2：收敛冲突能力

Alt 自动写入最初看似能减少人工操作，但它会与其他插件共同写入相同元数据，且无法可靠决定最终所有权。最终选择移除后台入口和 REST 写入表面，保留只读检测。

这形成了一条长期原则：当插件无法拥有某个内容真相时，优先提供诊断、预览和明确的人工处理路径，不用“自动化”掩盖所有权冲突。

### 阶段 3：保护高频公共路径

搜索统计属于附加能力，用户搜索才是主路径。严格限流因此只约束统计写入：站点级短时锁串行修改计数，每分钟最多 300 次；锁竞争、锁存储异常或上限到达时跳过统计，用户搜索继续执行。

同时增加每日词项上限、溢出聚合、坏数据归一化和存储压缩，解决短期并发与长期体积增长两个不同问题。

### 阶段 4：分批完成源码国际化

国际化按维护页、维护 REST/PHP、共享用户路径、模块元数据与 Admin React、旧 PHP 表面分批推进。稳定 ID、错误码、审计分类和用户输入保持原值，只在显示边界翻译。

POT 提取不能只相信命令退出码。构建流程把 PHP、TS/TSX 翻译调用、Registry/设置契约元数据和独立维护倒计时脚本合并，并通过契约测试抽查关键 `msgid`，防止把整段 TSX 源码误提取成 gettext 消息。

### 阶段 5：把翻译变成正式交付物

`en_US` 语言包包含 1,453 条译文。初稿使用本地模型辅助生成，同时保护 printf 占位符与 HTML 标签；随后对导航、保存、OSS、备案、数据库、媒体/WebP、评论、AI、隐私和动态格式串完成 152 项定向审校。

硬门禁结果：

- 0 空译文；
- 0 中文残留；
- 0 占位符不一致；
- 0 HTML 标签不一致；
- 0 临时 marker；
- `msgfmt --check --check-format`、`msgcmp` 和 `composer i18n:build` 通过。

独立英语母语全量审校尚无记录，但不作为本次技术交付阻塞项；真实用户反馈应通过增量修订语言包处理，不回退运行时或发布契约。

## 四、开发经验与可复用思路

### 1. 事实状态必须只有一个当前入口

历史台账可以保留旧 ZIP、旧环境和当时的未完成项，但必须明确标注“历史时点”，并链接到当前结论。新会话先读当前入口，再查历史证据，不能用全文搜索命中的第一条旧记录决定状态。

### 2. 完成定义必须包含交付链路

“源码已接入翻译”不等于“语言包已交付”；“ZIP 校验通过”不等于“该 ZIP 已在干净环境安装”；“本地 Plugin Check 通过”不等于“WordPress.org 已正式发布”。每个阶段都要写清实现、产物、真实环境和外部流程分别处于什么状态。

### 3. 主路径和附加路径要有不同失败策略

搜索、页面加载和设置读取是用户主路径；统计、诊断和外部探测是附加路径。附加能力失败时应降级、跳过或保留直达路径，不能把自己的失败传播为用户主操作失败。

### 4. 外部写入必须先确认所有权和清理能力

媒体元数据、对象存储 Bucket、远端测试对象和 WordPress.org 发布都涉及外部状态。进入前必须明确凭据权限、写入目标、回滚、清理责任和授权；没有这些条件只能记录为待真实验证，不能用模拟结果冒充完成。

### 5. 自动生成产物必须有语义门禁

生成成功只证明工具运行，不证明结果正确。POT、PO、JSON、ZIP 和构建清单都要验证关键内容、文件命名、占位符、路径哈希和发布资产完整性。能用契约自动证明的规则，不依赖人工记忆。

### 6. 一次只收敛一个模块

每个工作包开始前写变更信封，明确目标、非目标、公共契约、预期文件、禁止区域、门禁和回滚。没有进入条件的候选增强继续留在台账，不在发布收尾阶段顺手实现。

## 五、以后统一执行规范

### 开始前

1. 运行 `git status --short --branch`；
2. 阅读 README、本文和相关模块的最新开发记录；
3. 写变更信封并确定唯一聚焦模块；
4. 判断是否触及公共 API、用户帮助、docs-site 或发布资产；
5. 若涉及多仓库里程碑，在中央仓库运行质量矩阵。

### 实施中

1. 先建立可复现证据或失败契约；
2. 做最小范围修改，不混入无关重构；
3. 稳定 ID、错误码、审计字段和用户内容不翻译、不重命名；
4. 外部请求和写入设置超时、权限、失败降级与清理路径；
5. 每个阶段结束立即更新当前状态和剩余原因。

### 收尾时

1. 运行最窄有用门禁，再运行与风险相称的全量门禁；
2. 公共变化同步实现契约、内置帮助、README 和 docs-site；
3. 发布内容变化后重新构建唯一 ZIP，旧哈希和旧 PCP 结论作废；
4. 清理临时容器、卷、网络、测试用户、凭据、Transient、Cron 和测试内容；
5. 精确暂存本轮文件，核对暂存区、提交内容和远端 SHA。

## 六、后续建议顺序

后续不要同时启动全部遗留项，建议按真实资源依次推进：

1. 先选择实际要使用的一家 OSS 供应商，完成单供应商真实端到端验证；
2. 从真实站点选择 2–3 个主题/构建器代表组合做兼容窄测；
3. 随真实故障积累 AI 诊断案例，不为了凑数量构造“成功案例”；
4. 目标提交稳定后，再取得明确授权执行 WordPress.org 外部发布；
5. 根据真实用户需求决定其他 locale 或 P3 体验增强的优先级。

任何后续事项重新进入时，都必须重新确认目标版本、外部权限、数据清理方式和完成标准；本文的“建议顺序”不等于已授权执行。
