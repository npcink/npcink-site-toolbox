# Npcink Site Toolbox 项目开发经验与交付规范

## 1. 文档目的与适用范围

本文是项目的长期开发、验收和交付规范，归纳 2026-07 至 2026-08 的用户体验排查、功能收敛、并发限流、后台国际化、真实 WordPress 验证和发布收尾经验。它回答“为什么这样做”和“什么证据才算完成”，而不是替代代码注释或阶段性问题台账。

阶段证据、命令输出和逐项历史结论保留在[开发收尾与质量治理手册](开发收尾与质量治理手册-2026-08.md)；本文作为以后新会话、新贡献者和 AI 代理的入口规范。

## 2. 产品边界与职责边界

Npcink Site Toolbox 是面向站长的本地 WordPress 工具箱。变更必须留在现有插件功能面内，不把 Npcink Core、Toolkit、Adapter、Cloud Addon 或云控制平面的职责带入本仓库。

以下能力不属于本插件的真相源：AI 写入和提案批准、Provider Runtime、计费、队列、云端工作流、跨仓库发布状态。需要这些能力时，只能通过已定义的边界调用，不在本仓库复制一套“看似方便”的实现。

## 3. 事实优先的问题治理

用户视角问题先按可复现性、影响面和风险分类，再决定是否实现：

1. 先读 README、最近开发记录和当前状态，建立问题矩阵。
2. 区分真实行为缺陷、文案/可发现性问题、工具误报和暂时无法验证的外部依赖。
3. 为真实缺陷先写能证明旧实现失败的回归或契约测试，再做最小修复。
4. 任何“已完成”必须有代码、测试、真实环境或发布产物证据；没有证据的事项只能标记为待验证。

不要因为用户能绕过问题就降低优先级，也不要把偏好争议包装成 Bug。每个阶段结束时都要明确已完成、未完成、原因和再次进入条件。

## 4. 变更信封（编辑前必写）

每个工作包只聚焦一个模块或一组紧密相关的契约。编辑前在工作记录或 PR 描述中写出：

- 目标仓库和聚焦模块；
- 预期改动与明确非目标；
- 触及的公共契约（REST、设置、区块、文案、发布包等）；
- 预期文件，以及明确不能改变的文件/区域；
- 必跑门禁、真实环境验证和跨仓库矩阵要求；
- 回滚方式与数据清理方式。

非目标很重要：例如 Alt 写入冲突收敛时，目标是移除自动写入表面，非目标是重做 SEO 评分或批量媒体修复。

## 5. 分阶段开发流程

### 阶段 A：基线

运行 `git status --short --branch`，阅读 README 和相关开发记录，确认分支、脏文件和最近提交。涉及多仓库里程碑时，在 `/Users/muze/gitee/npcink-toolbox` 运行 `composer quality:matrix`，不要在本仓库复制矩阵脚本。

### 阶段 B：契约先行

先补激活路径、权限、输入校验、数据生命周期、版本一致性、平台兼容和国际化契约。契约名称描述业务不变量，避免绑定某个私有函数或 DOM 细节。

### 阶段 C：最小实现

先运行聚焦测试使旧实现失败，再改最小范围代码。不要在行为修复中顺手重构无关模块；每次只引入一个可解释的行为变化。

### 阶段 D：真实 WordPress

使用真实后台页面、`serialize_block()` + `do_blocks()`、真实 REST 请求和真实权限身份验证。Local 的 symlink 冒烟适合快速反馈，但不能代替精确 ZIP 的干净安装；至少覆盖声明的最低 WordPress/PHP 边界和一个当前支持版本组合。

### 阶段 E：发布候选

构建唯一候选 ZIP，记录版本、条目数、大小和 SHA-256。必须用同一个 ZIP 在干净环境安装、启用、访问后台/REST/区块，再运行官方 Plugin Check（PCP）。ZIP 内容改变后，旧的 PCP 结论全部失效，必须重新扫描。

### 阶段 F：收尾

临时容器、卷、网络、用户、应用密码、Transient、Cron、测试文章和测试对象逐项清理。最后检查工作区、暂存区、提交内容和远端是否一致。

## 6. 关键技术经验

### 6.1 冲突能力的取舍：检测优先于自动写入

Alt 自动写入会直接修改 `_wp_attachment_image_alt`，与 SEO、媒体管理和图片优化插件争夺同一字段。即使单次写入正确，多个插件的执行顺序也会造成覆盖和不可预测的“最后写入者获胜”。因此已移除自动写入路由和后台入口，保留缺失 Alt 的只读检测与提示。

通用原则：当能力会替其他插件写入其拥有的内容真相时，优先提供诊断、预览和可撤回的人工动作；只有边界、所有权和冲突策略都明确时才允许自动写入。

### 6.2 严格限流只约束统计写入

搜索健康的用户搜索是主路径，统计是附加路径。当前实现用站点级短时互斥锁保护 Option 更新，每分钟最多 300 次统计写入；竞争失败或锁异常时保守跳过本次统计，不阻断搜索。每日词项上限、溢出聚合和体积压缩共同防止长期无界增长。

通用原则：强一致只用于需要保护的数据写入；限流失败必须降级到“少记一条”，而不是让用户请求失败。不要把该承诺自动套用到所有 Transient 或外部计数器。

### 6.3 国际化必须验证产物而非命令

后台脚本通过 `wp-i18n` 运行时和 `wp_set_script_translations()` 加载翻译，PHP 与 TS/TSX 文案统一提取到 `languages/npcink-site-toolbox.pot`。动态句子使用完整占位符配合 `sprintf()`，让译者能调整语序；不要把一句话拆成多个不可重排片段。

`composer i18n:pot` 成功只说明脚本退出码为 0，不代表 TSX 文案真的进入 POT。必须抽查关键 `msgid`，并由国际化契约测试阻止回归。后台/PHP 文案清理应按页面和模块分批推进，未覆盖的页面不能写成“全量完成”。

### 6.4 发布警告的处理

PCP errors 阻塞发布；warnings 必须逐条判断、记录根因和是否为工具误报，不能使用 blanket ignore 隐藏。当前候选 ZIP 的两条核心 Hook 前缀 warning 已确认是 PCP 误报，仍保留在发布记录中。

## 7. 文档、契约与链接同步

公共 API 或用户可见功能变化时，实施契约、插件内置帮助、README 和 docs-site 教程必须同批更新；链接检查必须覆盖仓库内文档、发布 readme 和站点教程。内部开发规范不需要伪装成用户教程，也不应因此扩大 docs-site 范围。

文档要记录决策背景、替代方案、验证证据、已知限制和后续进入条件。不要保留过时的“已完成”表述；历史台账可以保留原始记录，但要链接到当前规范。

## 8. Git、提交与推送规范

暂存前运行 `git status --short --branch` 和 `git diff --stat`。只显式暂存本轮文件，不使用 `git add -A`。提交前检查 `git diff --cached --stat` 和 `git diff --cached --name-only`；提交后检查 `git show --name-status --stat HEAD`。得到明确授权后推送，并用 `git rev-parse HEAD` 与远端分支 SHA 比对。
