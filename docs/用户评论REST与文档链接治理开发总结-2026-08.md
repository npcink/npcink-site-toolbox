# 用户评论 REST 与文档链接治理开发总结

> 日期：2026-08-07
>
> 状态：开发节点已收口
>
> 范围：需求收敛、用户评论 REST、“我的评论”兜底页、插件内置教程、文档链接治理、发布包检查与真实站点验证
>
> 非范围：自定义用户角色实现、AI 服务运行时、云端队列、计费或跨仓库控制面

## 一、需求演进

本轮并非从一开始就有稳定的技术规格，而是经历了从概念到真实消费者的逐步收敛。

### 1.1 从“自定义身份”到候选提案

最初讨论的是创建用户角色并勾选 capability。该能力有明确的站点管理价值，但会涉及内置角色保护、最后管理员保护、角色所有权、用户迁移和多站点边界。在缺少真实使用场景时，直接实现会扩大插件的长期权限管理责任。

因此将其收口为 [自定义用户角色候选功能提案](自定义用户角色候选功能提案-2026-08.md)，明确标记“暂缓实现”。这一步的经验是：对高权限功能，先记录问题、准入条件和回滚原则，比先写界面更有价值。

### 1.2 从通用评论自助管理到 AI 评论助手

评论功能最初包含“有回复时匿名化为占位评论”等较完整的社区语义。当真实消费者明确为 AI 评论助手后，主要矛盾变成了：外部客户端如何以某个 WordPress 用户的身份，稳定地发布、修改和删除其自己的评论。

最终收敛为：

- 使用 WordPress 原生应用程序密码，不建立自定义 Token 系统；
- 使用 JSON REST API，不授予 `moderate_comments`、`edit_posts` 或 `manage_options`；
- 所有权一律使用当前认证用户 ID 判断；
- 支持查询、发布、修改、单条删除和最多 20 条的批量删除；
- 删除只进入 WordPress 回收站，不永久删除；
- 已有有效回复的评论不修改、不删除，避免破坏对话上下文；
- 修改使用 `expectedHash` 进行乐观并发校验，成功后重新进入待审核状态。

## 二、产品和架构决策

### 2.1 总开关与界面开关分离

“用户评论 REST 接口”是总开关，默认关闭。总开关关闭时不注册路由，也不注册“我的评论”菜单。

“显示‘我的评论’后台页面”是独立的兜底开关。关闭它不会关闭 REST，因此 AI 客户端可以只使用 API，同时站点管理员仍可按需提供浏览器内兜底操作界面。

这种“运行能力开关 + 辅助界面开关”模式可复用于未来其他 API 型功能。

### 2.2 认证和授权不是同一层

应用程序密码只解决“请求是谁发出的”。插件仍必须在每一次修改和删除时核对：

```text
comment.user_id === current_user_id
```

不能用评论者姓名、邮箱或客户端传入的 `user_id` 判断所有权。对不存在和不属于当前用户的评论统一返回 `404`，避免向其他用户泄露评论存在性。

### 2.3 优先复用 WordPress 原生语义

认证、用户、评论、审核状态和回收站均以 WordPress 核心 API 为事实源：

- `wp_new_comment()` 发布评论；
- `wp_update_comment()` 修改并重新进入待审核；
- `wp_trash_comment()` 删除；
- `WP_Comment_Query` 用当前用户 ID 查询；
- WordPress 原生应用程序密码执行 Basic Auth。

这样可以继续复用站点的评论审核、垃圾评论和回收站流程，并避免在 Site Toolbox 中维护平行数据模型。

### 2.4 批量操作采用有界、部分成功语义

批量删除每次最多 20 条，逐条返回 `deleted`、`alreadyDeleted` 或 `rejected`。不承诺数据库事务，也不因单条失败回滚已成功的处理。

此处的关键是让客户端能够对每个 ID 做准确决策，而不是用一个含糊的“批量失败”覆盖局部结果。`summary.deleted` 表示成功处理的数量，包含已在回收站的幂等结果。

## 三、真实验证过程

### 3.1 不使用后台 Cookie 代替应用程序密码

实测站点为 Local 环境 `magick-toolbox.local`。浏览器中的登录 Cookie 只用于确认用户名、开关和后台界面；REST 测试单独使用 Basic Auth 和应用程序密码，证明外部客户端的真实认证路径可用。

完整路径包括：

1. 未认证列表请求返回 `401`；
2. 应用程序密码认证的列表请求返回 `200`；
3. 发布评论返回 `201`；
4. 携带最新 `expectedHash` 修改返回 `200`，状态变为 `pending`；
5. 单条删除返回 `deleted`；
6. 重复删除返回 `alreadyDeleted`；
7. 新建两条评论后批量删除，返回 `deleted: 2`、`failed: 0`；
8. 在 `status=trash` 列表中确认测试评论全部进入回收站。

应用程序密码在工具交互中以隐藏输入传入，没有写入命令文本、仓库、文档或测试日志。密码一旦在对话或其他非保密渠道暴露，应立即撤销并重新生成。

### 3.2 本地 HTTP 不代表生产安全边界

Local 环境在 HTTP 下成功使用了应用程序密码，但这只证明本地联调可用。正式环境仍必须使用 HTTPS，不得为了迁就本地 HTTP 而放宽 WordPress 或生产环境的认证安全策略。

### 3.3 真实 HTTPS 站点验证

本地链路通过后，又在真实 HTTPS 站点使用专门账户和应用程序密码完成完整验证：认证列表返回 `200`，发布返回 `201`，修改返回 `200` 且进入 `pending`，单条删除返回 `deleted`，回收站能够确认测试评论，重复删除返回 `alreadyDeleted`，两条评论的批量删除全部成功。

这次验证补足了 Local 环境不能覆盖的 TLS、反向代理、生产 WordPress 配置和真实审核流程。测试只使用带唯一标记的临时评论，不操作既有业务评论；文档只记录结果，不记录用户名、应用程序密码、评论正文或具体评论 ID。

详细操作和凭据处理规则见 [用户评论 REST 生产验收与凭据处理规范](用户评论REST生产验收与凭据处理规范-2026-08.md)。

### 3.4 发布包与 Plugin Check

最终候选包通过 `pnpm --dir vite build`、`composer release:build` 和 `composer release:verify` 生成并验证。Plugin Check 2.0.0 对最终 ZIP 解压内容检查为 `0` 个错误、`16` 个既有警告；本轮新增帮助页最初产生的两个变量前缀警告已修复。

PCP 应检查最终安装包，而不是开发仓库。开发仓库包含测试、文档、依赖和源码，会产生与实际发布边界无关的噪声。既有警告即使确认是误报，也应在验收记录中分类说明，而不是无条件忽略。

## 四、文档和帮助页决策

### 4.1 基础教程必须随插件可用

最初“详情”按钮指向尚未完成部署的 `docs.npc.ink`。实际检查发现该域名的 TLS 证书不包含对应主机名，浏览器会在到达文档前就拒绝连接。

最终方案是在 WordPress 后台注册只读的隐藏帮助页，由 PHP 注入当前站点的 `admin_url()` 和 `rest_url()`。“详情”始终打开当前站的内置教程，而不把基础操作依赖于外部网站。

内置教程面向站点管理员，需要 `manage_options`；“我的评论”面向普通登录用户，只需要 `read`。两个页面的用户和权限边界不应混合。

### 4.2 文档不同表面各有责任

- [用户评论 REST 接口实现合同](用户评论REST接口-2026-08.md)：路由、参数、状态码、幂等性和安全边界的事实源；
- 插件内置帮助页：站点内始终可用的简明教程；
- [VitePress 用户教程](../docs-site/features/page-comment/user-comment-rest-api.md)：面向普通用户的完整说明和响应示例；
- README 和 WordPress.org `readme.txt`：只提供稳定入口和发布必需信息。

公开 API 改变时，必须同步检查这些表面，不能只修代码或其中一份教程。详细规则见 [链接维护规范](链接维护规范-2026-08.md)。

## 五、链接治理经验

全仓库链接审计将链接分为了四类：

1. 项目自有链接，可对 DNS、TLS、部署和重定向承担完整责任；
2. 第三方链接，可能有登录、反爬、区域和临时故障；
3. 站点内部链接，应使用 WordPress URL API 生成；
4. 占位和示例，只能出现在代码块、输入占位或测试数据中。

此次发现的问题包括：

- 未就绪的文档域名提前进入产品；
- “待完善”被通用表格无条件渲染为链接；
- GitHub 仓库从 `muze-page` 迁移到 `npcink` 后，多处公开文档仍依赖重定向；
- QQ 联系方式仍从 HTTP 起步；
- 历史 Gitee 地址没有明确标记为历史仓库。

修复后新增 `composer links:check` 离线合同门禁，检查当前仓库身份、未就绪域名、明文 HTTP 和 Markdown 内部目标。联网死链不作为每次 CI 的强制条件，因为第三方站点会因反爬、登录和区域限制制造假失败；发布前则必须对项目自有链接做真实 HTTP/TLS 检查。

## 六、调试与纠错经验

### 6.1 真实 WordPress 路径能发现合同测试看不到的问题

内置教程页最初使用“先注册子菜单，再 `remove_submenu_page()`”隐藏入口。真实 WordPress 会因菜单被移除而失去页面权限映射，直接访问时显示错误页。改用 `add_submenu_page(null, ...)` 后，页面保持注册但不显示菜单，真实点击验证通过。

这说明：后台页面不能只验证回调存在和字符串合同，还必须在真实 WordPress 中访问最终 URL。

### 6.2 工具命令失败不等于产品失败

本轮出现过三类假失败：

- Corepack 调用了与项目 `devEngines` 不一致的 pnpm，改用仓库已配置的 `pnpm` 命令后构建通过；
- 直接调用 Vitest 单文件时绕过了 Admin Vite 别名配置，改用 `pnpm --dir vite test:admin` 后全量通过；
- 链接检查器初版正则分隔符错误，并误扫描 `node_modules`；修正边界后才得到稳定离线门禁。

正确做法是保留第一次失败的证据，判断失败所在层，修正工具或命令后重跑，而不是直接改产品代码迁就错误的测试方式。

## 七、可复用开发规范

### 7.1 需求收敛

- 先确认真实消费者和主要任务，再决定权限、界面和 API；
- 高权限、高不可逆功能在缺少场景时只记录候选提案；
- MVP 应围绕真实自动化路径，不因为“可以做”就扩展全部管理能力；
- 对每个非目标明确记录，防止后续默认扩大范围。

### 7.2 REST 和权限

- 认证优先复用 WordPress 原生机制；
- 授权必须在资源层再次检查当前用户与资源所有者；
- 不为便利提升全局 capability；
- 列表必须分页，批量必须有硬上限；
- 删除默认选择可恢复的回收站或软删除；
- 修改需要并发保护，避免客户端用过期内容覆盖新状态；
- 状态码和错误码必须与真实实现一致，不记录“未来可能返回”的错误。

### 7.3 后台界面

- 运行能力和兜底界面可以分别开关；
- 帮助页不要干扰主菜单，但必须保留 WordPress 的注册和权限映射；
- 站内 URL 必须使用 `admin_url()`、`rest_url()` 或相对当前 `wp-admin` 的后备路径；
- 设置页只放简洁说明，完整教程使用独立帮助页承载；
- 服务端输出转义和客户端 DOM 构建都应将数据视为不可信。

### 7.4 文档和链接

- 基础教程随插件发布，外部文档是扩展而不是单点依赖；
- 项目自有 URL 在 DNS、TLS 和部署完成前不得对外生成链接；
- “待完善”、TODO 和示例值不得渲染为可点击链接；
- 仓库、组织和域名迁移后要做全仓库收口，不长期依赖重定向；
- 离线 CI 检查确定性合同，发布前人工或定期任务检查真实 HTTP/TLS。

### 7.5 验证

正常的收口证据应由五层组成：

1. PHPUnit 验证 PHP 合同、权限和边界；
2. PHPStan 验证静态类型和不可达分支；
3. Vitest 验证设置交互、链接渲染和生成契约；
4. 生产构建验证类型、CSS 隔离和发布产物；
5. 真实 Local WordPress 验证应用程序密码、菜单注册、点击路径和最终页面。

对涉及外部认证或第三方网络的功能，不能用后台 Cookie、mock 或只有 HTTP 状态码的结果代替真实路径。

正式发布时再增加两层：

6. 对最终 ZIP 执行发布结构校验和 Plugin Check；
7. 在真实 HTTPS 站点使用专门测试评论完成认证、增改删、幂等和批量操作。

## 八、当前维护合同

后续修改用户评论 REST 时，至少执行：

```bash
composer links:check
composer test
composer phpstan
pnpm --dir vite test:admin
pnpm --dir vite build
pnpm --dir docs-site build
git diff --check
```

发布前还要复验：

- REST 总开关关闭时路由不存在；
- “我的评论”关闭后 REST 仍可用；
- 应用程序密码的发布、修改、单删和批量删除；
- 其他用户的评论统一为 `404`；
- 过期 `expectedHash` 返回 `409`；
- 已有回复的评论不可修改或删除；
- 内置教程页的动态 API 地址、应用程序密码入口和权限；
- 项目自有链接的 DNS、TLS、重定向和最终落点。

生产冒烟的测试标记、凭据输入、失败处理和收尾清单统一遵循 [用户评论 REST 生产验收与凭据处理规范](用户评论REST生产验收与凭据处理规范-2026-08.md)。

## 九、留待后续的问题

- 自定义用户角色继续保持候选，不因本轮评论权限需求而默认进入实现；
- 当真实调用量证明需要时，再为认证用户的评论 REST 设计独立限流策略，在此之前文档不宣称会返回 `429`；
- 外部文档站完成 DNS、TLS和部署后，可以在内置帮助页底部增加“查看在线文档”，但不替换内置教程；
- 如果未来允许处理已有回复的评论，必须另行设计占位评论、隐私清理和评论树合同，不能直接放开当前删除分支。

## 十、回滚与停用

- 关闭 REST 总开关即停止注册所有用户评论路由和菜单；
- 只关闭兜底界面不影响已接入的 REST 客户端；
- 撤销应用程序密码可立即中断对应客户端的认证；
- 删除功能不会永久删除评论，测试数据和误操作仍可从 WordPress 回收站恢复；
- 停用或移除插件内置教程不影响 WordPress 原生应用程序密码本身。
