# 项目开发经验与思路规范

> 状态：当前有效
>
> 适用范围：Npcink Site Toolbox 的需求分析、代码修改、文档维护、测试、发布和问题复盘
>
> 本文是长期执行规范；具体版本的命令输出、ZIP 哈希和外部验收结果仍以对应的阶段证据文档为准。

## 1. 这份规范解决什么问题

历史开发中反复出现的退回原因，并不是单个文件不会写，而是把不同层次的“完成”混在了一起：源码能运行、测试通过、构建成功、ZIP 合规、干净 WordPress 能安装、WordPress.org 接受，这些是不同的事实。

本规范把历史经验归纳为一条可重复的工作链：

```text
问题事实 → 范围与边界 → 最小改动 → 源码合同 → 构建产物 → 精确 ZIP → 真实环境 → 证据归档
```

任何一环没有证据，只能标记为“未验证”，不能写成“已完成”。

## 2. 产品边界先于实现

- Site Toolbox 只负责站长侧的本地工具能力、设置、诊断和明确披露的外部集成。
- Provider Runtime、云端控制面、提案批准、计费、队列和跨仓库工作流真相不放入本插件。
- 当多个插件可能写入同一数据时，先判断所有权；无法拥有真相时优先提供检测、预览和人工处理，不用自动写入制造冲突。
- 外部写入必须同时具备授权、最小目标、失败处理、清理方式和回滚路径；缺一项就停留在“待真实验证”。

## 3. 每个工作包先写变更信封

编辑前写清：

| 项目 | 必须回答 |
|---|---|
| 聚焦模块 | 本次只改哪个功能或文档域 |
| 目标 | 用户问题和可观察结果是什么 |
| 非目标 | 明确不改哪些模块、数据和跨仓库边界 |
| 公共合同 | REST、设置 Schema、Registry、翻译、帮助、发布包是否受影响 |
| 预期文件 | 哪些文件会变化并进入 Git/ZIP |
| 禁止区域 | 哪些运行时代码、兼容层或外部资源不得触碰 |
| 验收门 | 最窄测试、真实 WordPress、发布门禁和链接检查 |
| 回滚 | 如何恢复代码、设置、测试数据和外部对象 |

没有明确完成标准的候选想法进入待办或提案，不在收尾阶段顺手实现。

## 4. 从审核样例扩展到问题类别

收到一个审核问题时，不只修被点名的行，而要扫描同一类别：

| 审核样例 | 同类检查范围 |
|---|---|
| 通用全局名 | 类、函数、常量、Option、Transient、REST namespace、AJAX action、handle、nonce、Cookie、浏览器全局和 localized object |
| 直接输出资源 | 所有 PHP 资源标签、内联事件、`javascript:` URL、动态 CSS/JS |
| 权限或 nonce | REST、AJAX、admin-post、读写删除、远程副作用、对象所有权 |
| 无效链接 | README、readme.txt、内置帮助、docs-site、服务条款和示例 URL |
| 非可移植文件名 | ZIP 全路径、大小写碰撞、构建资源 basename、语言包和压缩产物 |
| 压缩源码不可追溯 | 精确 tag/commit、公开源码目录、锁文件、构建命令和 ZIP 内容 |
| 远程内容规则 | CDN 改写、镜像、代理、字体替换、连通性检测和自动修复建议 |

## 5. 实现原则

### 5.1 公共事实源

Registry、设置 Schema、版本、slug、文本域、REST namespace 和生成式前端契约只保留一个事实源。代码、测试、内置帮助、README、`readme.txt` 和 docs-site 通过合同或链接保持一致。

### 5.2 主路径与附加能力分级

搜索、页面加载、设置读取和保存是主路径；统计、诊断、远程探测和缓存刷新是附加能力。附加能力失败时应降级、跳过或保留直达路径，不能阻断主操作。

### 5.3 安全与输出边界

- nonce 只证明请求意图，capability 才证明权限，两者不能互相替代。
- REST 每条路由都有 `permission_callback`；写入、删除和远程写入还要验证输入和对象所有权。
- 文本、属性、URL 和文章 HTML 按最终上下文分别使用 `esc_html()`、`esc_attr()`、`esc_url()` 和明确的 `wp_kses_post()` 边界。
- 固定 gettext msgid、context 和 text domain 使用源码字面量；动态拼接翻译字符串不作为目录规则的长期方案。

### 5.4 外部服务披露

每个外部服务都要写清触发条件、发送数据、存储位置、失败行为、Terms 和 Privacy 链接；没有必要或超出目录边界的能力直接退役，不保留隐藏入口。

## 6. 证据分层与完成定义

| 层次 | 证明内容 | 不能替代 |
|---|---|---|
| 源码合同 | 前缀、权限、转义、翻译、链接和 Registry 规则 | 真实环境行为 |
| 自动化测试 | 回归逻辑和边界不被破坏 | 发布 ZIP 内容 |
| 构建合同 | 前端、语言包和构建产物可复现 | WordPress 安装 |
| 精确 ZIP | 用户实际收到的文件集合 | 外部目录批准 |
| 干净 WordPress | 激活、HTTP、设置、REST、日志和真实插件行为 | WordPress.org 最终决定 |
| 外部审核/真实样本 | 目录规则或实际价值得到验证 | 代码单元测试 |

完成描述必须绑定版本、commit/tag、精确 ZIP SHA-256 和验收记录。ZIP 中任何文件变化都会使旧哈希和旧扫描结果失效。

## 7. 文档体系与同步规则

- `docs/` 记录内部治理、架构、发布、证据和历史；`docs-site/` 记录站长使用教程、配置说明和 FAQ。
- 用户可见功能变化必须同步实现合同、内置帮助、README、`readme.txt` 和适用的 docs-site 页面。
- 同一规则只保留一个事实源；阶段总结保存证据，不覆盖当前规范。
- 历史文件进入 `docs/archive/` 前，先补状态、迁移表和交叉链接，再运行 `composer links:check`。

## 8. 收尾清单

1. `git status --short --branch` 和 `git diff --stat`；
2. 运行最窄相关测试，再运行 `composer test` / `composer phpstan`（按风险选择）；
3. 运行 `git diff --check` 与 `composer links:check`；
4. 内容或构建变化时重新生成语言包和精确 ZIP；
5. 发布候选执行 `composer release:build`、`composer release:verify` 和 `composer release:wordpress-org-check`；
6. 精确暂存本次文件，核对 `git diff --cached --stat`、`--name-only`；
7. 提交后核对 `git show --name-status --stat HEAD`，再推送；
8. 记录未完成事项的原因、授权条件、清理方式和重新进入标准。

## 9. 历史经验的最终结论

- “本地通过”不是“目录可提交”；验收对象必须是精确 ZIP。
- “扫描器零错误”不是“永远安全”；每次发布使用最新规则并审阅 warning。
- “说明写了”不是“审核可追溯”；公开源码、构建命令和提交必须与 ZIP 对应。
- “自动化越多越好”不是目标；自动化应保护主路径、数据所有权和可回滚性。
- 最可靠的防回归方式是把经验写进合同测试、CI、发布脚本和单一文档入口，而不是依赖记忆。
